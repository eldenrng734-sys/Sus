# AI SALES ASSISTANT CRM - PROJECT GUIDE (MVP)

## 0. CONVENTIONS
- [HARD] = hard task. Each dev owns exactly 3 (see section 7).
- [SEC] = security-critical code: auth, tenant context/RLS, RBAC, webhooks.
- "Dev N" = team member N. Day 0 = setup. Build days = 1-15.
- Times are Asia/Dhaka. Paths are repo-relative.

## 1. PROJECT
Goal: 5 devs build a working, secure, multi-tenant AI Sales Assistant CRM (MVP) in 15 build days (5h/day) + Day 0.
Business value: সম্ভাব্য Customer-দের সংগঠিত করা এবং Follow-up সহজ করা (organize prospects, make follow-up easy).
Stack: Python 3.12 + FastAPI | PostgreSQL 16 | LLM API | n8n | React/Next.js | Docker.
Product: multi-tenant SaaS CRM. Many companies (tenants) share one app + one DB. Each company's leads, conversations, users, integrations, reports are private to it.

Lead journey: Capture -> one CRM record with history -> AI intent + classification + score -> assign rep -> n8n follow-up -> dashboard.

Features (feature | behavior | module):
- Lead Capture | website form, WhatsApp, Facebook/Instagram, manual, CSV | integrations, leads
- Lead Classification | AI: type, interest, priority, score | ai
- Intent Detection | AI: demo/pricing/support/info, buying stage, sentiment | ai
- Auto Follow-up | n8n reminders + approved follow-ups; stop on reply or opt-out | tasks, n8n/
- CRM Integration | own REST API + webhooks; HubSpot/Salesforce later (optional, post-MVP) | integrations, API
- Sales Dashboard | role-based: rep, manager, company admin | dashboard, frontend

## 2. NON-NEGOTIABLES
Security rule: never skip or weaken a security step to save time. Cut features instead.

Two-approval rule: any PR touching auth, tenant context/RLS, RBAC or webhooks needs the ring reviewer + Dev 1 (Dev 4 if Dev 1 is author). No exceptions.

Never cut: RLS, auth, webhook signatures, MFA, encrypted credentials, cross-tenant tests.

Responsibility split:
- FastAPI: decides who can see/do what; holds all business rules.
- PostgreSQL: system of record. Not in DB = did not happen.
- LLM: reads text, gives opinion (intent, score). Never changes data, permissions or sends messages.
- n8n: runs scheduled/repeated jobs. Always via our API, never direct DB.
- React: displays data, sends user actions to API.

## 3. GLOSSARY
- Tenant: one customer company.
- RLS: PostgreSQL row-level security; hides other tenants' rows even if app code forgets a filter.
- RBAC: role-based access control.
- JWT/refresh token: short-lived access token + rotating refresh token.
- Argon2id: password hashing; real passwords never stored.
- Webhook: external service (WhatsApp/Meta) calls our URL.
- Signature check: proves webhook came from the provider.
- Idempotency/dedup: same request twice = same effect as once.
- Structured JSON output: LLM answers in fixed schema, validated by Pydantic.
- Migration (Alembic): versioned DB schema change.
- PII: personal data (name, phone, email).
- OpenAPI: API contract, visible at /docs.

## 5. ARCHITECTURE
Flow (top to bottom):
1. Lead sources: website form, tracking script, WhatsApp, Facebook, manual, CSV
2. Integration layer: webhooks, signature check, validation, dedup (webhook_events)
3. FastAPI backend: auth, tenant context, RBAC, leads, tasks, conversations, API
   - PostgreSQL (RLS): system of record
   - LLM service: analysis only
   - n8n: reminders, follow-ups, notifications

Build ONE modular app first. Do not start with microservices, Kubernetes, a vector DB or an agent framework.

### 7.2 Team rules
- Mob first hour on Day 3 (RLS) and Day 7 (webhooks): all 5 on one screen, then split.
- Ring review: Dev1 reviews Dev2; Dev2 -> Dev3; Dev3 -> Dev4; Dev4 -> Dev5; Dev5 -> Dev1.
- [HARD] PRs need two reviewers.
- [SEC] PRs: see section 2 two-approval rule.
- Publish shared contracts (API conventions, capture service, dashboard queries) in the first hour of the day.
- Announce in chat before creating a migration (avoid Alembic multiple heads).
- Get one senior for ~1h on Days 3, 7, 14.

### 7.3 Daily rhythm
- 10:00-10:15 stand-up (yesterday, today, blockers)
- 10:15-13:30 build own feature
- 13:30-14:30 integration window: merge PRs, fix conflicts, run full tests
- 14:30-15:00 team demo + plan tomorrow

### 7.4 Git & quality
- Branches: main (release) <- develop (daily integration) <- feature/<dev>-<feature>
- Every PR: green CI (lint + tests) + required reviews
- API contract (OpenAPI) agreed BEFORE coding
- Small PRs; merge at least daily; no big-bang merge on Day 14
- Conventional commits: feat:, fix:, test:, docs:

### 7.5 Definition of Done (per task)
- Code merged into develop
- Unit/API tests written and passing
- Tenant isolation respected (no query without tenant context)
- Ring review done; [HARD] or [SEC] also approved by security approver
- Endpoint visible in /docs
- Demoed at end-of-day session

## 11. MULTI-TENANCY & RLS [SEC]
Design: one PostgreSQL DB, shared tables, tenant_id on every tenant-owned row, enforced by Row-Level Security. Built on Day 3, never added later. Do not simplify or skip anything here.

Rules:
- Never trust a tenant_id from the browser. Backend verifies user membership + role on EVERY request.
- RLS enabled with no matching policy = deny by default.
- Composite FKs include tenant_id (Company A's lead cannot link to Company B's user).
- App DB role: not superuser, no BYPASSRLS. Use FORCE ROW LEVEL SECURITY so table owners are covered.
- Apply the same policy to EVERY tenant-owned table.
- Large customers may later get separate schema/DB.

Policy template:
```sql
ALTER TABLE leads ENABLE ROW LEVEL SECURITY;
ALTER TABLE leads FORCE ROW LEVEL SECURITY;

CREATE POLICY leads_tenant_isolation ON leads
USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

Per transaction (transaction-local; safe with connection pooling):
```sql
SELECT set_config('app.tenant_id', 'verified-tenant-uuid', true);
```

## 13. LEAD CAPTURE
Sources:
- Website forms: form POST to FastAPI -> name, email, phone, requirement, consent, UTM
- Website activity: first-party tracking script -> page visits, pricing views, demo requests
- Facebook Lead Ads: Meta lead webhook + API fetch -> form fields, campaign, ad
- Messenger: Messenger Platform -> messages, conversation IDs
- WhatsApp: Cloud API -> messages, phone, history
- Manual/CSV: CRM form + import -> rep-entered details

ONE pipeline for every channel (write once, test once):
1. Endpoint receives webhook/form.
2. Validate request + check provider signature.
3. Skip if already processed (webhook_events); providers may send duplicates.
4. Find or create lead (dedupe by email/phone/external ID).
5. Store interaction/message.
6. Request AI assessment.
7. Assign lead + create task if rules say so.

Notes:
- Meta webhooks may contain only an ID; fetch details via API.
- Prefer official APIs over scraping.
- Disclose tracking; collect consent where required.

## 14. AI: CLASSIFICATION & INTENT
Principle: AI advises, our code decides. No autonomous agent.

Pipeline: get permitted history -> redact unnecessary PII -> structured prompt -> validate with Pydantic -> save with model + prompt version -> deterministic rules decide tasks/approval.

Example input: "I need a CRM for my 20-person sales team. Please arrange a demo this week."
Example output:
```json
{
  "category": "business_customer",
  "intent": "request_demo",
  "interest": "CRM software",
  "buying_stage": "consideration",
  "sentiment": "positive",
  "priority": "high",
  "lead_score": 90,
  "recommended_action": "schedule_demo",
  "follow_up_days": 0,
  "confidence": 0.94
}
```

Features:
- Classification: type, industry, product interest, customer category
- Intent: demo, pricing, support, info, complaint
- Scoring: value/urgency estimate, combined with rule-based signals
- Summary: summarizes long conversations
- Sentiment: positive/neutral/negative
- Recommended action: call, demo, email, follow-up

Rules:
- LLM never modifies data, assigns permissions or sends messages.
- Confidence < 0.6 (example threshold) -> mark for human review.
- Support Bangla + English; include both in evaluation set.
- Privacy: text sent to a hosted LLM leaves our server; pick a provider with suitable retention + contract terms.

## 15. N8N AUTOMATION
n8n runs repeated jobs. It never touches the DB; it calls our API like any client. FastAPI still enforces permissions, rules, tenant.

Workflows:
- A (new lead): event -> fetch lead via API -> AI assessment -> assign + task -> notify rep.
- B (follow-up): schedule -> due tasks from API -> check consent, opt-out, quiet hours, status, replies -> send approved message or request approval -> save result.
- C (customer reply): save message -> pause follow-ups -> re-run intent -> notify rep -> new task if needed.

Rules:
- n8n editor is private; customers never access/edit workflows.
- FastAPI <-> n8n: authenticated internal requests; no unrestricted DB access.
- Unique event IDs + idempotency keys prevent duplicate messages/tasks.
- Safe retries with logging; minimal PII in execution logs; set execution data retention.
- Stable encryption key stored outside workflow DB; keep n8n updated; TLS via reverse proxy.
- Licensing: Sustainable Use License may cover workflows we run for clients if they cannot access/change them. Customer-configurable workflows or white-labeling may need a commercial license. Confirm with n8n before launch.

## 18. SECURITY REQUIREMENTS [SEC]
Everything here is required for MVP.

Authentication: email verification, Argon2id, MFA for admins, single-use short-lived reset tokens, short-lived access tokens, refresh rotation + revocation, login rate limits, invite-only joining.

Risk -> protection:
- Cross-company leakage -> tenant verification, RLS, authorization tests
- Password attacks -> Argon2id, MFA, rate limits
- SQL injection -> parameterized queries / ORM
- Unauthorized APIs -> server-side auth + permission checks
- CSRF/XSS -> secure cookies, CSRF tokens, escaping, CSP
- Webhook spoofing -> provider signature validation
- Credential theft -> encryption, restricted access, rotation
- API abuse -> tenant-aware rate limits, validation, quotas
- Server attacks -> firewall, updates, monitoring

Data protection: TLS everywhere, encryption at rest, KMS/secrets manager for tokens, separate DB credentials (app / n8n / admin), no public DB port, encrypted off-server backups, audit logs, retention/export/deletion policy, logged temporary support access.
